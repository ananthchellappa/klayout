## Layering

Dependencies come from `src/klayout.pro` (`X.depends += Y`). Arrows point toward the dependency.

```
klayout_main ─► lay ─► layview ─► layui ─► laybasic ─► (gsiqt) ─► rdb, pex ─► db ─► gsi ─► tl
                 │       ▲                                                  ▲
                 ├► ant, img, edt ─┘                                        │
                 └► lym ─► gsi + (rba | rbastub) + (pya | pyastub) ─────────┘
drc ─► rdb, lym          lvs ─► drc          plugins ─► lib, lay, layview, ant, img, edt
buddies ─► drc, lvs, plugins                 pymod ─► db, lay, layview, edt, … (+ gsiqt)
```

Key consequences:

- `tl`, `gsi`, `db`, `rdb`, `pex`, `lib` build without Qt (`./build.sh -without-qt`). This "Qt-less core" is what the standalone Python wheel (`pip install klayout`) ships.
- Everything from `laybasic` upward needs Qt. `laybasic` itself is written to be mostly Qt-agnostic (`LayoutViewBase`), and `layview` adds the Qt widget (`LayoutView`).
- Ruby and Python are optional. When one is disabled, `rbastub`/`pyastub` take its place. DRC/LVS need Ruby because their DSLs are Ruby.

## The three ideas that make the codebase make sense

### 1. GSI: one declaration, two languages, plus the docs

Script APIs are never written per language. Each C++ class gets exposed once through a `gsiDecl*.cc` file next to it (e.g. `src/db/db/gsiDeclDbBox.cc`, `src/laybasic/laybasic/gsiDeclLayLayoutViewBase.cc`):

```cpp
gsi::Class<db::Box> decl_Box ("db", "Box",
  gsi::method ("width", &db::Box::width, "@brief Gets the width of the box\n") + …
);
```

- `gsi` (`src/gsi/gsi/gsiClass.h`, `gsiMethods.h`, `gsiSignals.h`) holds the reflection model: classes, methods, arguments with defaults, events (`gsi::event`), enums, and "extension" methods (`method_ext`) that bolt free functions onto a class.
- `rba` and `pya` walk that model at runtime and synthesize Ruby/Python classes. `pymod` packages the same thing as `klayout.db`, `klayout.lay`, etc.
- The `@brief …` doc strings become the API reference (Help → Class Index in the app, or klayout.de/doc/code/).
- `gsiqt` applies the same mechanism to Qt itself, generated by scripts under `scripts/`. That is why `pya.QTcpServer`, `pya.QDockWidget` etc. exist inside KLayout.
- So to find "what can a script do", grep `gsi::method ("name"` in `gsiDecl*.cc`.

### 2. The layout database (`db`)

- `db::Layout` owns cells (`db::Cell`), a layer table, the properties repository, and library/PCell bookkeeping.
- A `db::Cell` holds per-layer `db::Shapes` (boxes, polygons, paths, texts, edges) and `db::Instances` (`CellInstArray`, including regular arrays). Coordinates are integer database units (`db::Coord`, 32-bit by default); `D*` types (`DBox`, `DPoint`) are micron/double variants.
- Hierarchy-aware bulk geometry is `db::Region`, `Edges`, `EdgePairs` and `Texts`. Each has a flat (`dbFlatRegion`), "as-if-flat" and **deep** (`dbDeepRegion`, backed by `db::DeepShapeStore`) implementation. Deep mode is what makes DRC/LVS hierarchical.
- Netlist extraction: `db::LayoutToNetlist` (connectivity → `db::Netlist` of circuits/nets/devices/subcircuits, plus per-net shape clusters). `db::LayoutVsSchematic` adds a reference netlist and `db::NetlistComparer`, which produces a `db::NetlistCrossReference`.
- Stream I/O is a plugin registry: readers and writers live in `src/plugins/streamers/<fmt>/db_plugin` and register themselves (`tl::RegisteredClass<db::StreamFormatDeclaration>`). Each format also has a `lay_plugin` with its options UI.
- PCells: `db::PCellDeclaration` (C++) or `PCellDeclarationHelper` (Ruby/Python, `src/db/db/built-in-*macros/pcell_declaration_helper.lym`). A `db::Library` holds PCells and fixed cells and is registered globally.

### 3. Views, plugins and the dispatcher (`laybasic` → `lay`)

- `lay::LayoutViewBase` (`laybasic`) holds one or more `lay::CellView`s (layout + current cell path), the layer properties, and the renderer (`layRedrawThread*`, `layBitmap*`). Rendering is multi-threaded into bitmaps, while UI interaction stays on the Qt main thread.
- `lay::Plugin` / `lay::PluginDeclaration` (`src/laybasic/laybasic/layPlugin.h`) is the extension point for nearly everything interactive: edit services (`edt::Service`), rulers (`ant`), images (`img`), the netlist/marker browsers, the net tracer. Declarations register statically and contribute menu entries, config pages and mouse modes. Scripts get the same hooks through `lay.PluginFactory`/`lay.Plugin`.
- `lay::Dispatcher` routes configuration (`config_set`/`config_get`, persisted in `~/.klayout/klayoutrc`) and menu actions to plugins. `lay::AbstractMenu` is the declarative menu tree that both C++ and scripts insert into.
- Selection is owned by `lay::Editables`/`edt::Service`. Script access goes through `LayoutView.object_selection` (`ObjectInstPath`) and the `on_selection_changed` event.
- `lay::MainWindow` (in `lay`) is the `QMainWindow`. `lay::ApplicationBase` / `GuiApplication` / `NonGuiApplication` parse the command line, set up macro paths and run autorun macros.

## Startup sequence

`src/klayout_main/klayout_main/klayout.cc` → `GuiApplication` (or `NonGuiApplication` for `-z`/`-zz`) → `ApplicationBase::init_app` (`src/lay/lay/layApplication.cc:545`). It runs these steps in order:

1. Collect search paths: `~/.klayout`, `$KLAYOUT_PATH`, and salt packages in `~/.klayout/salt`.
2. Register the `macros/` (Ruby) and `pymacros/` (Python) folders on each path.
3. Run **autorun-early** macros.
4. Create the main window and load technologies.
5. Run **autorun** macros, then the `-r`/`-rm` scripts.
6. Enter the Qt event loop. Everything script-side runs on this single main thread.

Useful command-line options:
- `-e` / `-ne`: edit mode on/off.
- `-z`: no GUI.
- `-r f`: run a script and exit. `-rr f`: run it and keep the app open.
- `-rm f`: add a startup script. `-rd k=v`: set script variables. `-rx`: disable autorun.
- `-j dir`: add a macro folder. `-u session`: load a session.

## Conventions

- Namespaces match the module (`tl::`, `db::`, `lay::`, `edt::`, `gsi::`), and files are prefixed with it (`dbRegion.cc`).
- Exports use `<MOD>_PUBLIC` macros from `<mod>Common.h`.
- Style: two-space indent, a space before call parentheses (`foo (x)`), braces on their own line for functions.
- Prefer `tl::` facilities (`tl::Exception`, `tl::to_string`, `tl::Event`, `tl::DeferredMethod`) over raw STL/Qt where they exist.

## About Doxygen

The repo has no Doxyfile. The authoritative API reference is the GSI-generated class docs (built into the app; online at klayout.de/doc). A Doxygen pass would only help for C++-internal work. If it's ever wanted, restrict `INPUT` to `src/{tl,gsi,db,laybasic,layui,lay,edt}` and exclude `src/gsiqt`, which otherwise makes up two thirds of the input.
